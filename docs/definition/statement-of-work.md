## Statement of work template

### Title

Code Sentinel

### Abstract

This Statement of Work (SOW) outlines the objectives, scope, deliverables, roles, requirements, and timeline for the development and implementation of Code Sentinel, an AppSec Orchestration and Vulnerability Management Platform.

Code Sentinel will centralize security analysis for software projects by integrating multiple security scanning tools into a single platform. The system will orchestrate security scans, execute and manage security analysis processes, receive and process reports generated by integrated security tools, normalize their findings into a common internal structure, and provide a centralized interface for reviewing security results.

The platform will support project management, security scan execution and monitoring, security finding registration and classification, historical scan analysis, security dashboards, report generation and protected report downloads, user and role management, project assignment, and role-based access control.

The initial implementation will support Static Application Security Testing (SAST), Secret Scanning, Port Scanning, and Custom Security Scanners. The architecture will be designed to support the integration of additional security analysis tools and vulnerability types without requiring a complete redesign of the platform.

The implementation will be organized into three development sprints. Sprint 1 will establish the complete frontend experience using static data. Sprint 2 will implement the backend, authentication, authorization, database, scanner engine, integrations, and core security functionality. Sprint 3 will complete dashboards, historical results, protected reports, final authorization validation, and end-to-end testing.

### Value

The main value of this project lies in centralizing and standardizing security analysis results that would otherwise be managed independently across multiple security tools.

By normalizing findings from different scanners into a common structure, Code Sentinel will reduce the manual effort required to consolidate security results, improve visibility into the security posture of software projects, and provide a consistent reference point for AppSec analysts, developers, and administrators.

The platform will also provide traceability between projects, scans, tools, findings, severity, locations, and historical results. Role-based access controls will ensure that users can only access the projects and functionality assigned to them.

The project value includes platform architecture and design, frontend development, backend development, database implementation, security scanner orchestration, security tool integrations, result processing and normalization, user and project management, protected reporting, testing, documentation, and final implementation.

### Scope

The project involves the development of a web-based AppSec orchestration and vulnerability management platform that allows authorized users to register and configure software projects, execute security scans, monitor scan status, process results from multiple security tools, normalize findings, review vulnerabilities, generate reports, and consult historical security information.

The system will be intended for AppSec analysts, developers, and platform administrators.

# Context

## Present

### Identified Obstacles

* Security findings are distributed across multiple standalone tools, each with its own format and interface.
* There is no unified view of the security status of software projects.
* Consolidating results across tools requires manual effort.
* Different tools may use different naming conventions, severity classifications, and report formats.
* The lack of a normalized format makes it difficult to compare and query findings consistently.
* There is limited centralized traceability between projects, scans, tools, and findings.
* Access to project security information must be controlled according to user roles and project assignments.
* Security reports require controlled access to prevent unauthorized disclosure.
* Security analysis may involve sensitive source code and credentials, requiring local processing and secure storage mechanisms.

Currently, security analysis results are distributed across different tools, each generating reports according to its own format and structure. Security and development teams must review multiple tools to understand the security posture of a project. This makes prioritization, reporting, and historical analysis slower and less consistent.

Code Sentinel is intended to address these limitations through a centralized security analysis and vulnerability management platform.

## Future

With the implementation of Code Sentinel, the organization will have a centralized platform capable of orchestrating security scans and consolidating their results.

Authorized users will be able to manage projects, execute scans, review findings, filter results, consult historical scans, and view security overviews. Administrators will be able to manage users, roles, and project assignments.

Reports will be protected through the defined report password mechanism, and report downloads will require the appropriate authorization.

The architecture will support the addition of new security scanners without requiring a complete redesign of the platform.

Future expansion may include additional security analysis types such as DAST, SCA, IaC, and container scanning, subject to separate scope definition and approval.

## Requirements

The system shall provide the following functional and non-functional capabilities as part of the MVP.

### Functional Requirements

#### RF-001: User Registration

The system shall allow platform administrators to create user accounts. User self-registration is not required as part of the defined administrator-controlled account management model.

#### RF-002: User Authentication

The system shall authenticate registered users before granting access to protected platform functionality.

#### RF-003: Project Registration

The system shall allow authorized users to register software projects for security analysis.

#### RF-004: Project Configuration

The system shall allow authorized users to configure registered projects, including the information required to perform security analysis.

#### RF-005: Security Scan Execution

The system shall allow authorized users to initiate security scans against registered and authorized projects.

#### RF-006: Scan Status Management

The system shall track the status of security scans, including pending, running, completed, and failed states.

#### RF-007: Scan History

The system shall retain previously executed scans and allow authorized users to consult historical scan information.

#### RF-008: Security Tool Integration

The system shall support the integration of external security scanning tools.

#### RF-009: Security Tool Orchestration

The system shall orchestrate the execution of configured security tools as part of a security scan.

#### RF-010: Security Result Collection

The system shall collect the results produced by integrated security tools.

#### RF-011: SAST Analysis

The system shall support Static Application Security Testing to identify vulnerabilities in source code.

#### RF-012: Secret Scanning

The system shall support security analysis for exposed secrets, credentials, API keys, and similar sensitive information.

#### RF-013: Port Scanning

The system shall support port scanning as a security analysis type.

#### RF-014: Custom Security Scanners

The system shall support the integration and execution of custom security scanners.

#### RF-015: Multiple Analysis Types

The system shall support multiple security analysis types within the same platform and project workflow.

#### RF-016: Report Format Processing

The system shall process the report formats generated by integrated security tools.

#### RF-017: Result Normalization

The system shall normalize results from different security tools into a common internal data structure.

#### RF-018: Security Tool Identification

The system shall identify the security tool responsible for generating each security result or finding.

#### RF-019: Finding Registration

The system shall register security findings generated by supported security analysis tools.

#### RF-020: Finding Classification

The system shall classify findings according to their supported vulnerability type or classification.

#### RF-021: Finding Location

The system shall retain the relevant location information for findings when such information is provided by the source security tool.

#### RF-022: Finding Severity

The system shall retain and display the severity associated with each finding when provided by the source security tool.

#### RF-023: Finding Association

The system shall associate findings with the corresponding project, scan, and security tool.

#### RF-024: Centralized Results

The system shall provide a centralized view of security results collected from supported security tools.

#### RF-025: Finding Visualization

The system shall provide an interface for visualizing security findings and their relevant information.

#### RF-026: Finding Filtering

The system shall allow authorized users to filter findings using supported attributes such as severity, type, tool, project, scan, or other defined criteria.

#### RF-027: Scan Results

The system shall provide authorized users with access to the findings and security results associated with completed scans.

#### RF-028: Historical Results

The system shall allow authorized users to consult and compare relevant security information from previous scans.

#### RF-029: Security Overview

The system shall provide a dashboard or overview representing the security status and findings of authorized projects.

#### RF-030: Extensible Security Architecture

The system shall provide an architecture that allows additional security scanners and vulnerability types to be integrated without requiring a complete redesign of the platform.

#### RF-031: Admin User Management

The system shall allow authorized administrators to create, edit, activate, deactivate, and delete user accounts.

#### RF-032: Admin Access Restriction

The system shall enforce authorization rules that restrict platform functionality and data according to the user's role.

#### RF-033: Report Password

The system shall protect reports using a defined password mechanism. The final mechanism for establishing and managing the report password shall be agreed upon before implementation of this requirement.

#### RF-034: Protected Report Download

The system shall prevent unauthorized users from downloading protected reports and shall require the appropriate authorization or report password before permitting access.

#### RF-035: Project Assignment

The system shall allow authorized administrators to assign projects to users and shall enforce those assignments when users access projects, scans, findings, and reports.

## Non-Functional Requirements

### NFR-001: Confidentiality

The system shall protect sensitive security information, including source-code analysis results, findings, credentials, reports, and project information from unauthorized access.

### NFR-002: Integrity

The system shall maintain the integrity and consistency of projects, scans, findings, reports, users, and security results throughout their lifecycle.

### NFR-003: Availability

The system shall provide reliable access to the platform and its functionality during the agreed operating periods, excluding scheduled maintenance.

### NFR-004: Secure Credential Storage

The system shall store authentication credentials, security-tool credentials, and other sensitive secrets using appropriate secure storage mechanisms and shall not store passwords or secrets in plaintext.

### NFR-005: Extensibility

The system shall use an architecture that allows additional security tools, scanners, report formats, and vulnerability types to be incorporated without requiring substantial redesign of existing core components.

### NFR-006: Common Data Structure

The system shall represent normalized security findings using a common internal data structure that allows results from different security tools to be stored, queried, displayed, and compared consistently.

### NFR-007: Local-Only Processing

Security analysis processing and handling of project source code shall be performed locally according to the defined system architecture. The system shall not require unauthorized external processing or transmission of project source code for the execution of supported security analyses.
